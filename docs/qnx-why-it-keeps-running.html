Why QNX keeps running when parts of it crash

QNX can crash. It is built so one crash stays small: one broken part dies, gets restarted, and the stop code keeps running.

Three reasons: the core is tiny, every other part runs in its own walled-off box, and the most important code always runs first. The Arduino covers the last case: the whole Pi dies.

The stop code always goes first

  • Real time means predictable, not just fast. The stop happens within a known, bounded time, every time.
  • In your code: give the stop thread the highest priority, and give the AI thread a normal one.

What to say to judges

Say

  • "Each part runs in its own protected box, so one crash can't take down the stop code."
  • "The stop thread runs at the highest priority, on the device, with no cloud."
  • "Built on the OS family certified for cars and factory machines."

Don't say

  • "QNX can't crash." It can; it just contains the crash.
  • "SafeStop is safety-certified." The free version is not the certified product.
  • Specific timing numbers you haven't measured.
"The stop decision runs at the highest priority on a microkernel OS built for cars. If the Pi ever goes quiet, the Arduino stops the machine within 200 ms."

Q2 · Fri Nov 20, late

I give it a program and it runs. What else is it connected to?

Yes: you SSH in, run python3 safestop.py, and it runs. The difference is what happens underneath: every device is a separate driver program, and your code talks to it through the kernel.
